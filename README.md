# DeepThreat

A modular, local web app for Sleeper fantasy football leagues, with per-player shortcuts to current X posts and news coverage.

## Windows app

Run `release\DeepThreatSetup.exe` to install DeepThreat for the current Windows user. The installer creates Start Menu and optional desktop shortcuts; later installers upgrade the same installation while keeping saved connection settings.

The app opens in Firefox when available, otherwise in a resizable Edge app window. Your Sleeper username, manager, and last selected league are stored locally under `%APPDATA%\DeepThreat`. Use the small key button beside the season selector to clear them and return to the connection page.

## Run from source

1. Install Python 3.10 or newer.
2. From this folder, install dependencies: `python -m pip install -r requirements.txt`
3. For Ask AI, save a free Gemini API key in `api-key.txt` in this folder. The rest of the app does not need it.
4. Start the app: `python run.py`

The launcher starts a local-only server on an available port and opens it in Firefox (or Edge if Firefox is unavailable).

## Put it on the web

The same app runs on a Python host. `wsgi.py` is the application object a platform's WSGI server imports, and `waitress` is the server it is served with. `DEPLOY.md` has the whole of it — the two variables that matter (`SECRET_KEY` signs the session cookie; `GEMINI_API_KEY` is only for Ask AI), the start command, the health check — which also names the commit the copy is running, so a deploy that has fallen behind says so rather than looking like the newest one — and what a free instance does differently — and `render.yaml` and the `Dockerfile` are that same setup expressed for a platform.

Nothing has to be provisioned alongside it: every page reads Sleeper over HTTPS at request time, so a hosted copy needs no database, no volume and no inbound access. The one file it reads from its own image is the History page's season summaries in `data/history/` — what each finished season added up to, so a cold copy rebuilds that page instead of reading every week of every season again — refreshed with `python tools/build_history_snapshot.py`. The connection you last opened lives in the browser's session, and served, that is the only place it lives: the settings file beside the app is not read or written there, because one file on an instance everybody can reach is every visitor's memory rather than yours, and it would open your league to whoever found the URL. Connecting is then a one-time step per browser — and `DEEPTHREAT_REMEMBER_FILE=1` puts the file back for a copy that really does have just one user.

Because the address is public, the app also keeps its own time: `robots.txt` and an `X-Robots-Tag`
header ask crawlers to stay out, and `services/rate_limit.py` counts every request, per visitor
and across the whole instance, so a walker or a loop is refused with a `429` instead of spending
the instance and the Gemini quota. DEPLOY.md has the counts and how to change them.

## Check the page layout

The brand logo in the toolbar is positioned absolutely, floating above the heading band, so heading text has to keep out of its lane. `python tools/check_layout.py` drives a real browser over every page mode the app links to, at widths on both sides of the 981px breakpoint, and fails if the two ever overlap. It starts its own server and checks the league already saved in your settings; install the extra tooling first with `python -m pip install -r requirements-dev.txt`.

Exit code 0 means no overlap, 1 means text runs through the logo, and 2 means a page could not be measured — never silently a pass, because the logo only renders once Sleeper returns the account's leagues. Add `--base-url http://127.0.0.1:PORT` to check an app you already have open, or `--json out.json` to keep every measurement.

## Check the lineup slots

The Matchups page's slot view reassigns a team's starters into best-scoring eligible slots. Three things have to stay true of that answer, and none of them is visible when it breaks — the page still renders, and a figure that has quietly moved is not an error a reader can see: every starter is placed in exactly one slot, a team's columns add up to the score the matchup records, and Group View is exactly the slot view collapsed to wide positions. `python tools/check_lineup_slots.py` runs all three over every scored team-week of the connected league and reports each promise on its own, so a failure says which one broke and on which team's week.

The same check runs in CI on every push and pull request (`.github/workflows/lineup-slots.yml`), against a finished season already committed under `data/history/` so the figures are frozen and the run needs no account or secret, and `render.yaml` waits for the repository's checks before deploying (`autoDeployTrigger: checksPass`) so a commit that breaks one of the promises is not released. Render's own `preDeployCommand` is the other place a pre-deploy command could go, but it is paid-only; see DEPLOY.md.

Two seasonal pages read the same weekly assignment over a season-long window, and the check reconciles both against it: the Season tab's points-per-slot, times the games it counts, is compared with the weekly slot buckets added up over the same weeks, and each Player Data season row is compared with the weekly matchup records for that player over the same weeks. The Player Data tables carry the bench as well as the starters, so they are reconciled against the weekly records the slot view reads rather than the slot buckets, which hold starters alone. Every section prints how many rows it compared and the worst difference it found, and a section that compared nothing fails instead of passing quietly.

Exit code 0 means every promise held, 1 means one broke, and 2 means the league could not be read or a comparison could not be made. It reads Sleeper directly — no browser, no running app — and leaves your saved connection as it found it. Use `--weeks 4,5,6` for a range of the weekly check, `--weekly-only` to skip the two seasonal comparisons, `--league-id` for another league, or `--json out.json` to keep every week's outcome.

## What a page sends

Two things keep a first load small, and both are the kind of change that has to be checked on
the page rather than trusted to a diff:

- **The logo the pages load is not the PNG master.** `static/deepthreat-arc-logo.webp` is the
  same 1519x670 picture as `static/deepthreat-arc-logo.png` in a third of the bytes (284 KB
  against 840 KB), encoded losslessly, so no pixel and no dimension differs and nothing about
  where it sits or how sharp it looks changes at any window width or screen density. The PNG
  stays as the master `packaging/make_icon.py` draws the Windows icon from; regenerate the web
  one with `python tools/make_web_logo.py`, which refuses to write a file that is not the
  master's own pixels.
- **Stylesheets and scripts are cached for a year, and their URLs are what makes that safe.**
  Every one of them is written with `asset_url(...)` in `app.py`, which stamps the URL with a
  digest of the file's own bytes: an edited file is a new URL, so nobody is ever shown a cached
  copy of the old one, and a page view stops re-asking for files that have not changed. A
  static file asked for at a URL without a stamp keeps the revalidate-every-time header, so the
  long cache and the stamp cannot come apart.

## What's new

The notebook to the right of Ask AI opens the changelog: what changed in this app, newest first, in the words of somebody using it rather than somebody building it. `services/changelog.py` is the only place an entry is written, and the panel in every page's toolbar reads that list and nothing else — no league, no Sleeper, no request of its own — so one entry appears on every page at once.

`python tools/draft_changelog.py` does the first half of the writing: it gathers the commits after `COVERED_THROUGH` — the last commit the file already speaks for — asks the same Gemini model Ask AI uses for the reader's version of them, and prints the lines to edit, or with `--write` puts them at the top of `RELEASES` and moves the anchor to `HEAD`. It never invents a figure, it says so when it has to fall back to the commit subjects, it refuses to write that rough version into the file, and it points at any line that still names something a reader cannot open.

One line per change, a few words and never more than a sentence. A **performance** line is a page that used to be slow and is not any more, with the number if there is a real one; a **visual** one is something that looks different; a **functionality** one is something the app can do now that it could not before; and a line nobody would notice from the outside is an **also**, which is printed last and in smaller type. How it was done is not a line at all — no file names, no class names, no "single-flight": a reader cannot check those and has no reason to. Adding a release is one dict at the top of `RELEASES`: a date, a headline in the reader's words, and its lines as `(kind, text)` pairs, newest release first. The date and title of the newest one are what the button's dot compares itself against, so a release that has not been opened yet is what makes the dot appear.

## Modules

- `run.py` starts the local server and opens Firefox; `wsgi.py` is what a hosting platform serves instead.
- `services/local_settings.py` stores the per-user connection settings outside the install folder — and keeps nothing at all when the app is served, where the session is the memory.
- `services/history_digest.py` keeps what each finished season of a league added up to, so the History page rebuilds it instead of reading every week of matchups and transactions again — from memory, from a file beside the app's other data, or from the snapshot a deployment ships.
- `services/rate_limit.py` counts requests per visitor and in total, so a public copy cannot be walked or looped.
- `services/changelog.py` is the changelog the notebook beside Ask AI opens: one entry per change, written for the person using the app, and the only place a change is described for them.
- `app.py` defines the page routes.
- `services/sleeper.py` handles Sleeper data: the league's own records, the NFL schedule, and Sleeper's per-player NFL game log, which is the one place it says which team a player played for in a week and who he faced.
- `services/matchups.py` builds weekly position-group score comparisons.
- `services/player_card.py` builds one player's schedule, weekly points and season total.
- `services/player_pace.py` projects one player's 17-game pace for the stats his position is judged by, from his own NFL game log and the league's own scoring; it is also the only place a pace line is worked out, so the row under a player's card and the row he gets in a ranking are one calculation of the same games.
- `services/player_data.py` builds the weekly and season Player Data views.
- `services/league_tools.py` answers individual questions about one league's players, games, trades, draft picks, rosters, standings and how a player is pacing; it is what Ask AI is allowed to look up, and its league-wide pace read is what both the pace ranking and the Pace board are built from.
- `services/pace_board.py` builds the Pace board's rows and columns from that read, so the page, an answer and a card show one projection of one set of games.
- `services/ask_ai.py` runs the Ask AI question: it gives the model those lookups, runs what it asks for, and returns the answer with the lookups listed.
- `services/ask_model.py` finds the Gemini key and names the model.
- `services/seasonal.py` builds the Season table and its modes.
- `static/player-card.js` opens the player card from any player name, on a click, generates the card's 17-game pace table when its button is pressed, and sets a second player beside it from the box underneath.
- `templates/pace.html`, `static/pace.js` and `static/compare.js` are the Pace board: every player's pace line in one table, sorted by any column in the browser and narrowed by a position chip, with the compare panel on it — down the right of the page, and above the board on a window too narrow for the two columns — two players' paces side by side, the camera button that saves the card and the button that copies its address.
- `templates/` contains the pages; `static/style.css` contains the visual styling.
- `tools/check_layout.py` measures the heading text against the brand logo in a real browser.
- `tools/check_lineup_slots.py` proves the slot assignment places every starter, sums to each team's official score, and keeps Group View equal to the collapsed slot view, and reconciles the Season tab's slot averages and the Player Data season tables against the same weekly numbers.
- `tools/make_web_logo.py` writes the lossless WebP the pages load from the PNG the Windows icon is drawn from.
- `tools/build_history_snapshot.py` writes the History page's season summaries into `data/history/` for a deployed copy to rebuild from, and verifies the rebuilt page is byte-identical to the one built from Sleeper.
- `tools/draft_changelog.py` drafts the notebook's next release from the commits since `COVERED_THROUGH`, for a person to edit rather than trust.

The player hub opens X's live search and Google News search for one player at a time. It does not fetch results for the full roster in the background.

## Trades

The Trades page lists one manager's own trades beside the whole league's, for one season or one week of it. The column is the connected manager's by default, and a dropdown in its header points it at any manager the league has had — the manager is followed by his Sleeper user id rather than by a roster, so a rename does not split him in two, a manager who has since left the league is still one the column can show, and every sentence and label in it is written from whoever is being shown: "Your Trades — You sent", or "bkodae's Trades — bkodae sent". Opening a week of somebody's trades is that week of *those* trades, and a search made while a manager is being viewed keeps him. Above both columns sits one search box, and it reads every season the league has played, because a career is not a season: type a player's name, a team's name, a manager's username, or a pick ("2025 1st", "2.02", or a year on its own — "2024" — for every 2024 pick that changed hands). Names are matched loosely — part of a surname, a missing letter or a swapped pair all count — but only the players and teams this league has actually traded can be found. A typed name is read as a player's first and as a team's only when no player answers to it, since teams are often named after players. A team is followed by its manager, whose user id survives a rename, so searching a team name finds the seasons it traded under that name and the ones it traded under an earlier one.

A traded pick is a button, because what a manager wants from one is what it became. Clicking it opens a panel with the player taken with it, the place in the draft that happened ("1.08", overall 8) and the team that made the pick, then the route the pick took to get there, each hand-off with the week it was filed. However many teams it passed through, the panel ends with a player: the draft's own order places the pick, and a seat that order leaves out — a slot nobody holds, or one held by a manager who has since left the league — is placed by the team the trades say ended up with it, which is the team that made that seat's pick. Where the last recorded move and the draft's own seat disagree, the player is still named and the missing move is said beneath him. A pick whose season has not been drafted yet says so instead, because there is no player to name. A page can be open on an earlier season, and a pick looked up from one is read the same way: the trace — and every search — is anchored on the newest season of the league's chain rather than on the season being shown, so a 2023 pick seen from the 2019 page still names the player taken with it instead of reporting a draft that has since been held as one that has not happened.

## Ask AI

Ask AI answers questions about one league from that league's own Sleeper records — a player's weekly points and the last time he scored under a total, the exact place a player was drafted ("3.04, the 28th pick overall", and whether it was the startup or the rookie draft) together with whose pick it was and the trade that brought it there — the team it came from and what each side received — who a round of a draft held, the trades a team made and what each side received, what became of a draft pick that was traded, a season's records and its champion, a whole set of players ranked by their best single season ("which third round picks have scored the most in a season"), and the league ranked by what each player is on pace for in the season being played ("who is on pace for the most points this season"). It is an ordinary tab beside History, and every page links to it.

How one player has done against one NFL team is read from Sleeper's own per-player game log rather than from this league's records: the league scores only the weeks it played and never records which NFL team a player faced, so "what does he average against the Texans" is answered from Sleeper's official NFL game data — the team he played for in each week, the opponent, and that game's stat line — with every game scored by this league's own scoring settings. That is what makes an average here readable beside the weeks this league did score him, and it is the same scoring, not a different format: the app's own scoring reproduces the league's weekly figures exactly for the games both cover. It reaches back before the league's first season and includes weeks he was never on a roster here, which is what "all-time" means for a player; the answer says which seasons and how many games it covers, and names the games as a table of season, week, opponent, his team and points. A team is matched by name or code — "Texans", "Houston", "HOU" — including the codes a club wore before it moved, so games Sleeper filed under OAK are the Raiders' and under SD the Chargers'. Asked without a team, the same games are totalled per NFL team, which is how one player's best and worst opponents come back as a table.

A question that compares many players is answered by adding up the entire set and ordering it, not by naming the best of the handful that happened to be looked up. Every player the league drafted in that round is assembled, each one's weeks are summed into season totals, and the best of those totals is what gets ranked — so the ranking behind "which third round picks scored the most" covers all of that round's players, rather than a few flattering game logs. A week the season has not finished is not read, a week that scored nothing is not a game, and a filter narrows the set to a draft round, a draft year or a position; a season alone ranks that season's scores.

The same set is ranked by what each player is on pace for when the question is a projection rather than a record: "who is on pace for the most points this season" is answered over every player the league has scored in the season being played, each projected over a full season at the rate he has earned it at, and not over the best season anyone has already had. The same ranking covers every stat a position is measured by — passing and rushing yards, attempts, receptions, receiving yards, touchdowns, turnovers, points and points a game — so "who is on pace for the most rushing yards" and "the most receptions" are asked the same way; a stat only the positions that carry it are ranked by, which is why a question about a stat a position does not have is answered by saying so. Points are this league's own scoring and the other stats are Sleeper's official weekly figures, which is where a player's card reads them from too. It counts a player's games the way his card does — a week the league scored and that Sleeper recorded him taking the field in — so a row reads beside the pace button on the card it names, and a position narrows the ranking to one. Each row of it is that player's whole pace line rather than only the stat the question named: a rank of the league's points pace still shows what each player is on pace for in the stats his own position is measured by — a back's yards and catches, a quarterback's passing and turnovers — so the table can be read across the stats as well as down the ranking, and a stat a position is not measured by is left as a dash in his row rather than read as a zero. A season can be named to project it instead, and the ranking says which stat and season it projects and from how many weeks. The same read is the Pace tab, so an answer and the board behind it can never disagree — the board is that ranking with every column on show and each one sortable.

An answer takes the shape of the question, and prose is kept for the one thing it is good at: one fact is a sentence or two, several facts about one thing — a player's draft and where his pick came from, a trade and what each side received — come back as a two-column table of what was asked and what the records say, a set of things that share fields — a round of a draft, a week's scores, rosters' records, players ranked by their best season — comes back as a table of its own, and a set of things that do not, such as a list of trades, comes back as one line each. The rules the model writes to are in the `SYSTEM_INSTRUCTION` of `services/ask_ai.py`, and every one of those shapes is drawn by the app rather than sent to the page as markup. A figure is stated with the season and week it belongs to, and a draft pick is never a round guessed from a nearby pick.

A position in an answer wears the same badge every roster row wears, and a draft pick a gold chip of its own, so both can be picked out at a glance — in a table and in a sentence alike. The app reads those out of the answer's own text: QB, RB, WR, TE, DEF and DST as whole words, and a pick as the year and the round ("2025 1st") or a place in one ("3.04", "3rd Rd (3.10)"). A place is only read as a pick where a pick word sits beside it or the column is one that names picks, so a table of weekly scores keeps its figures as figures, and a figure is never dressed as a pick.

A draft pick is never reported by where it landed alone: the pick behind a drafted player is named with the team it originally belonged to and the trade that moved it, with what each side gave and received, whether or not that was asked for. Where a pick cannot be traced — Sleeper's draft order leaves out the slot, as it does when the manager who held it has left the league — the answer says so rather than leaving the reader to assume the pick was never traded.

The answers are written by Gemini (`gemini-3.5-flash`). The model is never handed the league and is never shown another one: it is given a fixed set of read-only lookups — player game logs, trades, draft picks, rosters, standings, weekly scores, draft boards, season rankings, the league's record book, and one player's own NFL games against a named NFL team — and the answer is assembled from what those return, so a figure in an answer is a figure the app read out of the league itself. The lookups behind an answer are listed under it. A traded pick is placed in its draft by the draft's own order, so "what did this pick become" is answered with one pick and the rookie taken there — and a pick that changed hands, however many times, still ends with the player it became: a seat the draft's order leaves out is placed by the team the trades say ended up with the pick, which is the team that made that seat's pick. Where the last recorded move and the draft's own seat disagree, the seat still names the player and the disagreement is reported beside him, because a move missing from Sleeper's feed is not a reason to leave the question unanswered. Only where the records genuinely cannot settle a question — a season holding two drafts, or two teams' picks of one round that cannot be told apart — does the answer say so rather than choosing.

One question costs several calls to the model, so a tier that is slow is felt: measured here, a single call to one took 27 to 76 seconds, which made a question of three lookups a wait of minutes, while the tier used now answers the same call in about a second. So a call is given 25 seconds, and a model that has not answered by then — or that answers with the API's own "high demand" — is passed over for the next model in the chain rather than failing the question. A rejected key is not passed over: it would fail everywhere, and it is reported.

It needs a free Gemini API key, and it is off until one is present — the tab appears only when a key is found. Save the key in `api-key.txt` beside the app, or in `%APPDATA%\DeepThreat\api-key.txt` for an installed copy, or set `GEMINI_API_KEY` in the environment. The key file is read from the app folder or the per-user settings folder, is never bundled into the Windows build, and is never shown back in the app.

The Matchups page loads one selected week at a time, features the connected manager's matchup, and compares points by lineup slot. QB and Superflex are combined as QB; all regular flex slots are combined as FLEX regardless of who filled them. It opens on the slot view, which reassigns only players who started in that matchup into best-scoring eligible slots, with slot labels and order derived from the league's starting lineup settings. Its Group View switch, in the row over the matchups, shows the submitted lineup grouped by wider positions instead, without leaving the page — and being the one control over the week, it turns every matchup on the page over at once. Its week tabs run through the regular season and then the league's playoff rounds, named P1, P2 and so on with the final called SB — one round a week, as many rounds as the league's own playoff bracket holds, so the rounds can be browsed before any of them has been played. A playoff round is a week like any other here: the teams that have an opponent are shown, and a team left without one is not on the page. The Season tab offers the same two views and opens on the same one, and compares each team's average slot production with the league average for that same slot, using the same weeks the Player Data Season tables count — every week the league has scored, and the week in progress as far as it has been played. A team's live week joins those averages only once every one of its starters' games is final, so a half-played week cannot score a team by how many of its players had already kicked off; the week it is counted through matches Player Data.

The Impact Players tab is hidden for now. Its pages and routes stay live, so opening a page with `?impact=1` still works, and setting `show_impact_players` to `True` in `app.py` puts the tab back on every page that links to it.

## Compare and Pace

The compare panel sits on the Pace board: two players' paces side by side, so a trade debate is settled without leaving the board it is read from. Two names are typed into two boxes — matched loosely, part of a surname is enough, and a name you start typing is finished for you — and the panel projects each over a full season at the rate he has earned his points at; the same lookup Ask AI answers a trade question with, so the panel and an answer can never disagree. It is always there and has nothing to fold away: down the right of the page, on the board of every position as much as on a board narrowed to one, where the board and the panel share the width the page already has and the board, not the page, is what scrolls if they ever need more room than there is. The page is no wider for it, and the panel's two boxes are stacked rather than set side by side, which is what leaves that column narrow enough for the widest board — the board of every position, twelve columns against a one-position board's nine — to fit beside it: that board's columns are drawn closer together than the shared table style draws them, so all of them still fit. On a page too narrow for the two columns the panel goes back above the board, at the width the page has. The board in view — the position chip and the column it is read by — travels with the search, so returning to the board returns to the one that was being read. A comparison no longer needs its own tab: the two names live on this page, and the address they make reopens the comparison for whoever opens it. Points, points a game and total touchdowns are compared for any pair, and the stats only one position carries (an RB's scrimmage yards next to a WR) are listed underneath the table instead of being dropped from it, because otherwise the two columns would read as the whole of both players.

A comparison can also start at the player rather than at the page: a card's generated pace has a box under it, and the name typed there puts a second column beside the first without leaving the card. The card's own player goes by his id rather than by his name, because a league can hold two players who read the same — this one holds two Frank Gores — and the card is not in doubt about which one it belongs to. The second player is the one typed, and a name that matches nothing leaves the pace that was already generated up and says why, rather than replacing it with an error.

The card is the thing that gets shared. The camera button saves exactly that panel as a PNG — names, both columns and every figure inside it — using the same screenshot tooling the matchup cards and Season tables use, so what arrives in the chat is what was on screen. The button beside it copies the page's own address, which reopens the same comparison with the same figures for whoever opens it, and needs no key, no account and no second lookup. Both buttons sit outside the card, so neither appears in the picture they take.

A comparison is of the season being played. The season switcher projects a season that is already finished instead — "compare their 2024 paces" — and the card says which season it projects and how many games each side is drawn from. A pace counts only the weeks this league scored and that Sleeper recorded the player on the field for, exactly as the pace button on a player's card does, so a bye and a week he sat out are neither of them a game on either side of a comparison.

The Pace board is the whole league's board: every player this league has scored on a row of his own, with what he is on pace for over a full season in every stat his position is judged by — points and points a game, and a quarterback's passing yards and turnovers, a back's rushing, receiving and scrimmage yards, a receiver's receptions, yards and touchdowns. It is the ranking Ask AI answers a pace question with, given a page: both read the same lookup (`services.league_tools.pace_lines`), and that lookup works a pace out with the same arithmetic behind the pace button on a player's card, so a figure on the board, in an answer and on a card are one figure rather than three that happen to agree today. The board opens on points, because that is chiefly what a pace is.

Clicking a column head sorts the board by it, which is what makes "who is on pace for the most rushing yards" a click rather than a question; a first click on a column of figures reads it from its top, so points open highest first and a name opens at A. The position chips narrow the board to one position, and it then shows that position's own stats — a back's board carries rushing yards, catches, receiving yards, scrimmage yards and touchdowns instead of a column of dashes. A stat a position is not measured by is a dash in his row, because he has none of it rather than none of it so far, and a dash sorts to the end of its column whichever way the column is read. The season switcher projects a season already finished the same way the compare panel does, keeping the position in view, and a name opens the same player card it opens everywhere else, which draws the same pace again. The board can be saved as an image with the camera button beside it.

Clicking a player's name — on the Matchups page, or on any Player Data table — opens that player's card: his headshot, the rate he scores at with the games behind it, his NFL schedule for the season with the fantasy points he scored in this league each week, and his season total. Clicking the name again closes it, as does clicking anywhere else, pressing Escape, or scrolling the page; nothing opens merely because the pointer passed over a name. The list covers the league's whole season, its playoff rounds included, marks bye weeks, dims the weeks the league has not scored yet, and counts a week as a game only when Sleeper recorded him on the field — so a bye or a week he sat out shows a dash and stays out of the total. The weeks it counts are the weeks the Player Data Season tables count — every week the league has scored, and the week in progress as far as it has been played — so the rate and the games behind it read the same as the tables a card is opened from, and nothing a player has already put on the board during a live week is missing from either. Points come from the same weekly matchup records the rest of the app reads, so a card agrees with the season views, with one deliberate difference: a card totals everything a player scored this season even if he changed teams, where the Team tab counts only the weeks he spent with the team that holds him now. A player who has not taken the field yet is another: the season tables print 0.0 for him, and the card says it has no rate instead.

The Player Data page shows one week at a time, or the season so far. Its Season tab lists every rostered player's points per game by position in the same tables the week views use, and its Team tab groups those same numbers by roster. Both season views can drop each player's lowest or highest week from the totals. They run past the end of the regular season into the league's playoff weeks, which count once the league has scored them, so a finished season reads whole — up to a 17-week sample for a league whose playoffs end in week 17. The week in progress is one of those weeks as far as it has been played: Sleeper records what each player scored as each game finishes, so a player whose game is over has it in his totals and one whose game has not started yet does not. The week tabs here are the same ones the Matchups page shows, playoff rounds included, and a week opened on a round says which round it is.
